系统的核心不是“桌面 UI 调一个 Agent SDK”，而是一个以 Pi Session 为唯一执行事实源、以 Studio/App 承载产品元数据、以 Runtime 提供宿主能力、再通过 Electrobun RPC 投射到桌面体验的本地优先工作台。

Runtime topology

四个运行上下文，一条执行权链

Desktop renderer、Desktop Bun、共享产品/执行内核与 CLI/ACP edge 在进程和依赖上分离，但最终都落到同一 Pi 语义。

Critical path

一次 Run 的完整执行主链

普通 Playground 与 Project Experiment 的差异停留在产品元数据和 binding 解析；commit 后的 transcript 与恢复语义统一由 Pi Session 控制。

01React intent

ThreadPlayground 从每个 tab 独立的 Zustand store 发起 run。

02Execution adapter

Playground/Project pane 附带目标 id、lane、leaf 与 draft。

03thread.* RPC

Namespaced client 穿过 Electrobun envelope；不是 Command。

04Product admission

Studio/App 校验产品状态，解析并冻结 operation binding。

05Durable Pi

写 operation、调用 model、顺序执行 tools，处理 Step/Continue。

06Durable effects

Tool approval 可挂起并跨重启恢复；writer lease 避免并发写。

07Projection refresh

UI 从已提交 Pi entries 重建所选 lane/leaf，不把流式草稿当事实。

当前 schema 断点：Studio 2 → 5

schema 2 使用 engine_thread_id 与 studio_run_references.run_id；schema 5 使用 Pi 的 session_id 与 studio_operation_references.operation_id。当前实现只创建全新 v5 数据库，并主动拒绝旧版本，避免把 Engine 数据静默丢弃。

迁移不是 ALTER TABLE

完整迁移需要重建 Pi Session、lane/leaf、operation entries、immutable binding，并将 Playground/Experiment 引用切换到新 identity；直接把 migration version 改成 5 会制造语义损坏。

Architectural invariants

边界、约束与禁止回退

这些规则不是风格偏好，而是防止第二执行循环、状态双写、生命周期泄漏和传输耦合重新出现。

必须保持

  • Pi Session 是 transcript 与 execution state 唯一事实源。
  • Feature 自有 contract、server、client、contribution 和稳定 id。
  • Window scope 在 Registry 之后清理，process resource 由 DesktopLifecycle LIFO 清理。
  • Renderer controller 管理 epoch、stale suppression、mutation ordering 与 rollback。
  • @llm-space/ui 只通过 HostServices、ModelClient 与 ExternalThreadExecutionRuntime 接入宿主。
  • Agent operation binding 在 admission 时冻结，恢复时不重新解析环境。

禁止回退

  • 不创建 aggregate RuntimeClient、catch-all native module 或 central business token registry。
  • 不让 Desktop 使用 ACP，也不让 Pi runtime 依赖 ACP。
  • 不让 UI 包导入 Electrobun、desktop client 或 server-only entrypoint。
  • 不把 application class 变成 contribution，也不通过 service locator 拉依赖。
  • 不在 presentation effect 中恢复 RPC 生命周期与持久化排序。
  • 不混用旧 Engine API 与新 Pi API 来“兼容两边”。

Risk map

风险热点与演进建议

优先级来自架构耦合与故障半径，不是代码质量评分。

Schema 2 → 5 数据断层

当前通过 fail-fast 保护数据，但会阻断已有用户启动。需要明确“导出旧 Engine 数据”还是“一次性迁移到 Pi”的产品策略与回归 fixture。

Desktop composition 复杂度

Window DI、Contribution、Registry、native attach 与 disposal 顺序高度相关。新增 feature 必须通过现有 stable-id module 路径进入。

异步 UI 竞争

Catalog、settings、auth、share dialog 都有 stale response 风险。controller epoch 与 serialized mutation 是必要结构，不应下沉到组件 effect。

Renderer bundle 体积

共享 UI + CodeMirror + 复杂 Thread editor 已逼近构建内存边界。CI 的 production Vite build 是发布前不可替代的信号。

双 runtime 语义同步

TypeScript prompt renderer 与 LangGraph Python generator 必须同步 variables、filters、exists 与 include；只做 TS snapshot 不足以证明行为。

唯一扩展点冻结

ToolRegistry 是当前唯一内部 extension seam。过早引入动态插件、renderer contribution 或 runtime enable/disable 会扩大权限与生命周期模型。
